# 生成中心精简建议

更新：2026-09-08。状态：建议与页面引导已完成；以下业务合并尚未实施，须在后续功能阶段确认后执行。

## 从现有项目看到的问题

1. 不是简单重复按钮，而是两条独立生成链路。普通生成经 backend/app/services/job_application_service.py 的 tailor_for_job，可信生成经 evidence_service.py 的 generate_trusted_tailor。App.tsx 左栏使用 trustedTailor，右栏使用 selectedBundle（来自 tailorBundles）。用户容易误以为左右是同一材料的生成与审核。
2. 可信链路有实际价值：只使用确认卡片，保留逐条引用与接受状态；普通链路有版本编辑、预览、招呼语和 PDF 导出。应合并操作入口，不能直接删除事实审查或出口限制。
3. 原资料卡片编辑界面已被新资料工作台前端替代，但新工作台尚未接上解析、确认卡片服务。不能把“没有可用证据”归咎于用户操作，也不能声称上传后现在即可进入可信生成。
4. 旧提示让用户到“下方岗位池”选岗位，但岗位已经独立成页。本轮修正为可点击的跨模块入口。
5. Agent 名称、路由和编排事件是诊断信息，不适合单独占据用户导航。本轮只移除运行页；后台执行及仪表盘用量保留。

## 推荐的用户流程

选目标岗位 → 选择真实资料 → 生成一份材料 → 在同一结果区审核、编辑、导出。

- 岗位雷达负责搜索与选岗；生成中心直接接收目标岗位，不再填写第二遍。
- 资料工作台负责上传、解析、事实确认；生成中心仅选择引用，不再建第二套资料库。
- 推荐经历作为默认准备步骤或同一个生成动作的前置检查。只保留一个主生成按钮，避免用户判断两种结果分别在哪。
- 主结果区提供“简历 / 招呼语”切换；证据引用与修改差异放在可展开详情中。事实风险必须显式提示。
- 用户编辑后仍要重新核验；保留定稿与导出门禁，不能用“简化”绕开真实性保障。
- 投递仍由岗位/投递流程负责，并保留平台预检与人工二次确认；不要把生成按钮变成自动投递。
- 技术日志与模型路由建议放入系统设置高级诊断。普通用户只看当前任务、失败原因与下一步。

## 后续实施顺序及验收

1. 接通资料工作台到真实上传、解析、确认卡片，并标明不支持格式/失败/处理中；先完成这个依赖，再承诺可信生成可用。
2. 以同一个材料 ID 串联两类生成结果、编辑版本、引用状态和预览，处理岗位切换时旧结果归属。迁移保留已有数据。
3. 将结果审核统一到右侧，左侧仅保留目标与资料准备；选择简历或招呼语不额外调用模型。
4. 编辑、定稿、PDF 导出必须读取同一最新版本；待核验材料禁止导出，不得因合并降低证据检查标准。
5. 增加空资料、无岗位、生成失败、重复点击、切岗、编辑后失效、定稿及导出一致性测试；通过后再接入投递。

本轮未合并接口、未自动调用模型、未上传私人文件、未改变真实平台操作权限。页面上的说明区是现状说明，不是新功能已实现的宣称。
